# H.6.1 P0 — LiveDB_ACE Read-Only Remediation Plan

**Status:** PLANNING ONLY — **not authorized for implementation**  
**Date:** 2026-10-15  
**Source finding:** [H6.1_LIVEDB_READ_ONLY_BOUNDARY_AUDIT.md](./H6.1_LIVEDB_READ_ONLY_BOUNDARY_AUDIT.md) (R21)

This document prepares a DBA-coordinated cutover so the portal’s HIS verification path is **read-only at the SQL permission layer**, while portal writes remain on `ACE_ResultsPortal`.

**No logins, grants, env files, application code, or services were changed while producing this plan.**

## 2. Target credential separation

### 2.1 Target architecture

```text
┌─────────────────────────────┐
│  ACE Results Portal (Node)  │
└─────────────┬───────────────┘
       ┌──────┴──────┐
       ▼             ▼
 DB_USER /        HIS_DB_USER /
 DB_PASSWORD      HIS_DB_PASSWORD
 (portal)         (HIS read-only)
       │             │
       ▼             ▼
 ACE_ResultsPortal   LiveDB_ACE
 (read/write app)    (SELECT only on approved objects)
```

| Pool | Env vars | Database | Intended privileges |
| --- | --- | --- | --- |
| Portal | `DB_USER`, `DB_PASSWORD`, `DB_DATABASE=ACE_ResultsPortal` | `ACE_ResultsPortal` | App read/write on portal schema only; **no** LiveDB write; ideally **no** LiveDB access at all after cutover |
| HIS | `HIS_DB_USER`, `HIS_DB_PASSWORD`, `HOSPITAL_DB_DATABASE` or `HIS_DB_DATABASE=LiveDB_ACE` | `LiveDB_ACE` | **SELECT only** on approved objects; not `sysadmin` / `db_owner` / `db_datawriter` |

Application code already supports this via `loadHisDbConfig()` (`HIS_DB_USER` / `HIS_DB_PASSWORD` optional overrides). **Config change is required at cutover; no code change is strictly required for separation**, though script updates are recommended (Section 4).

### 2.2 Exact LiveDB objects and minimum permissions

Derived from `lib/db/src/repos/hospital-patients.ts` (runtime verification):

| Object | Operations in app | Required grant for HIS RO login |
| --- | --- | --- |
| `LiveDB_ACE.dbo.vwReportPatientProfile` | SELECT (TOP, filter by demographics / patid) | **SELECT** |
| `LiveDB_ACE.dbo.vwPatientMstrList` | SELECT (JOIN / filter by PatientID, `isDied`) | **SELECT** |
| `LiveDB_ACE.dbo.psPatRegisters` | SELECT inside EXISTS (legacy demographics path) | **SELECT** |

**Do not** grant by default:

- `db_datareader` (entire database) unless DBA proves view-only grants are insufficient  
- `db_datawriter`, `db_ddladmin`, `db_owner`, any server role  
- INSERT/UPDATE/DELETE/EXECUTE on base patient tables  
- CONTROL / ALTER ANY *

**Optional later (not required for current app SQL):**

- SELECT on additional discovery objects used only by `inspect-livedb-schema.ts` — prefer updating that script to the RO login with an explicit allow-list, or keep it DBA-only.

**CONNECT** to `LiveDB_ACE` is required for the HIS login.

### 2.3 Portal identity end-state on LiveDB_ACE

After HIS RO login is verified in production:

| Right | Target for portal `DB_USER` on `LiveDB_ACE` |
| --- | --- |
| INSERT / UPDATE / DELETE / ALTER / DDL | **None** |
| SELECT on HIS views | **None** preferred (forces all HIS traffic through HIS pool) |
| CONNECT | **None** preferred, or CONNECT without object SELECT if DBA requires residual catalog visibility |

If other hospital systems **require** the current elevated login to retain LiveDB rights, then:

- Portal runtime **must** stop using that login (move portal `DB_USER` to a **new** least-privilege portal login for `ACE_ResultsPortal` only), **or**  
- Keep elevated login out of the Node process entirely.

Preferred long-term (two new dedicated logins):

1. `ace_results_portal_app` — rights only on `ACE_ResultsPortal`  
2. `ace_results_his_ro` — SELECT-only on the three LiveDB objects  

…and retire portal use of the shared elevated login. Staging may be: (A) add HIS RO first with shared elevated portal login still present but unused for HIS; then (B) replace portal login. **Do not leave production HIS pool on the elevated login.**

## 3. Cross-database (three-part name) access

### 3.1 Current risk

Portal pool sessions can resolve `[LiveDB_ACE].…` (verified). Scripts such as `probe-livedb-identity.ts` intentionally use three-part SELECTs via the portal pool. Any future bug or ad-hoc script using three-part **DML** would be allowed today under `sysadmin`.

### 3.2 Safe removal sequence (conceptual — not executed now)

1. Deploy dedicated HIS RO login + configure `HIS_DB_*` on app.  
2. Verify all runtime HIS paths use `hisRequest()` (already true for `hospital-patients.ts`).  
3. Update maintenance scripts to use HIS pool / HIS RO credentials (no portal-pool three-part LiveDB access).  
4. **Only then**, with DBA approval and dependency sign-off: remove portal login’s LiveDB CONNECT/SELECT (and any mapped user), or move portal app off the elevated login entirely.  
5. Re-test: portal pool `SELECT TOP (0) … FROM [LiveDB_ACE].sys.tables` should **fail**; HIS pool patient verify should **succeed**.

### 3.3 Rollback for cross-db lockdown

If portal features break because an overlooked path still used three-part LiveDB access:

- Prefer **code/script fix** so the path uses the HIS pool with the dedicated RO login.  
- If an emergency SELECT path on the portal identity is unavoidable, DBA may temporarily grant **SELECT-only** (not sysadmin / not datawriter) on the three approved views — with the same exceptional controls as Section 4.2.  
- **Do not** roll back to `sysadmin` / `db_datawriter` on LiveDB for “convenience.”  
- **Do not** restore shared elevated credentials into the Node HIS pool as a default recovery step.  
- Public exposure remains NO-GO regardless.

### 4.1 Fail-closed behavior (default after HIS cutover)

Once dedicated `HIS_DB_*` credentials are configured:

| Condition | Required behavior |
| --- | --- |
| Dedicated HIS login cannot authenticate, connect, or SELECT required objects | **Fail closed:** HIS-dependent patient verification / hospital lookup returns a safe error or deny. Do **not** silently switch to the portal/`DB_*` identity. |
| HIS path unhealthy | Portal features that do **not** need LiveDB may continue if `ACE_ResultsPortal` is healthy. Do not disable the HIS credential split to “keep verify working.” |
| Operators notice verify failures | Fix the RO login, grants, network path to SQL, or app config **while keeping `HIS_DB_*` set to the RO identity**. Open an incident if service impact warrants it. |

**Default rollback is not** “unset `HIS_DB_*`” and is **not** “point HIS at the old shared elevated login.” Those actions reintroduce the audit FAIL (R21) and are forbidden as routine recovery.

### 4.2 Rollback and recovery conditions

| Failure | Approved recovery | Forbidden |
| --- | --- | --- |
| HIS verify fails after C2/C3 | Fail closed (§4.1). Diagnose/fix HIS RO login, SELECT grants on the three objects, connectivity, or config typos. Keep dedicated `HIS_DB_*` configured. | Unsetting `HIS_DB_*` so the app falls back to elevated `DB_*`; pointing `HIS_DB_*` at the shared elevated login as a routine step; expanding public exposure |
| Portal writes fail after D1 | Revert `DB_USER` / `DB_PASSWORD` to the prior **portal** login **for `ACE_ResultsPortal` only**, without restoring LiveDB write rights to that identity for Node HIS use | Re-granting LiveDB `sysadmin` / `db_datawriter` for convenience; configuring HIS pool to that elevated login |
| Unexpected other-app outage after D2 | DBA restores **that app’s** required grants per A1 inventory — scoped to the other consumer, not blanket sysadmin for portal Node | Leaving Node HIS pool on an unrestricted identity as steady state |

### 4.3 Exceptional temporary restoration (not default)

Restoring any elevated or shared LiveDB-capable identity into the Node HIS path is **not** a standard rollback. It is allowed **only** as a break-glass exception when **all** of the following are true:

1. **Explicit dual approval:** DBA **and** system owner approve in writing.  
2. **Documented incident or change ticket** with business justification and named approvers.  
3. **Strict time limit** (window end recorded; auto-expire expectation stated in the ticket).  
4. **Verified network containment:** public Patient/Doctor exposure remains **NO-GO**; origin stays LAN-/Access-contained per current H.6.1 posture (no widening of firewall Any/Any or public DNS for this exception).  
5. **Exit criteria defined before start:** how elevated HIS credentials will be removed from the Node runtime and dedicated `HIS_DB_*` RO restored.  

When the exception window ends, operators **must confirm** that:

- Old elevated credentials are **not** present in the Node HIS configuration as steady state (`HIS_DB_*` = dedicated RO again, or HIS features remain fail-closed offline — never silent elevated fallback).  
- Evidence of final effective permissions is re-captured (Section 5).  
- Public Go/No-Go remains separate and stays **NO-GO** until R21 acceptance criteria are met.

### 4.4 Steady-state rule

Normal portal operation **must not** depend on an unrestricted HIS identity. Fail-closed HIS verification is preferred over reintroducing shared elevated credentials into the runtime. Any §4.3 exception is time-boxed, ticketed, dual-approved, and network-contained — and must not be left in place as the production configuration.

## 9. Acceptance criteria for **this remediation** (future)

Remediation of R21 is accepted when **all** are true with dated evidence:

1. Runtime HIS pool uses distinct `HIS_DB_USER` (not fallback to `DB_*`).  
2. HIS identity is not `sysadmin` / `db_owner` / `db_datawriter` on `LiveDB_ACE`.  
3. HIS identity has SELECT-only on the three approved objects (or DBA-documented equivalent minimal set).  
4. Portal runtime identity cannot write to `LiveDB_ACE`.  
5. Patient verification and portal writes verified per Section 5.  
6. No patient data leaked into evidence packs.  
7. Fail-closed HIS behavior is documented and operational (§4.1); recovery does **not** treat elevated shared credentials as default rollback.  
8. Written confirmation that old elevated credentials are **not** restored to the Node HIS path as steady-state configuration.  
9. Any §4.3 exception (if used) is closed, ticketed, and dual-approved with network containment evidence.  

**H.6.1 overall acceptance** and **public Go/No-Go** remain separate decisions.
