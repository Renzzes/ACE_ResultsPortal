# H.6.1 Independent Architecture Recommendation (Deliverable D)

**Author role:** Planning recommendation from evidence on FILESERVER1 / ACE Results Portal source  
**Not an implementation authorization**

---

## Executive recommendation

**Use one root domain with four subdomains, Cloudflare Tunnel to loopback origin, Cloudflare Access (MFA) on Staff/Admin, public Patient/Doctor with WAF/rate limits, and mandatory application Host gating.**  

Do **not** treat subdomain DNS as isolation. The product is still one Node process and one SPA. Network controls hide the origin; Access gates staff/admin; **server-side Host + RBAC** enforce portal boundaries.

**Public exposure status today:** **NO-GO.**

**Owner decision alignment (2026-10-15):** Staff/Admin via Cloudflare Access **DECIDED**; root domain `acemccebu.results.com` **SELECTED** (ownership unverified); staged remediation with separate public launch **DECIDED**; access-code expiry/rotation before public launch **DECIDED** (design pending); IdP **OPEN** (evaluate — prefer hospital IT-managed). See [H6.1_DECISION_REGISTER.md](./H6.1_DECISION_REGISTER.md). These recordings do **not** authorize implementation.

## Answers to required questions

### 1. Is one root domain with four subdomains best?

**Recommended choice:** Yes, for this hospital deployment.

**Evidence:** Single deployable at `D:\ACERPTS\app`; unified SPA routes (`/portal`, `/physician`, `/admin`, staff paths) in `App.tsx`.

**Reasoning:** One zone simplifies certificates, Tunnel ingress, and branding. Security comes from Tunnel + Access + Host gating + RBAC, not from buying four domains.

**Alternatives:** Separate public vs internal domains — stronger organizational split, higher cost/DNS complexity; warranted only if compliance demands it.

**Downside:** Shared zone means a Cloudflare account compromise affects all hostnames — mitigate with CF admin MFA and scoped API tokens.

**Validate:** After cutover, confirm cookies are host-only and CORS rejects cross-portal browser origins.

### 2. Safest practical way to publish Patient/Doctor while restricting Staff/Admin?

**Recommended:** Cloudflare Tunnel + Node on `127.0.0.1:3003` + Access on staff/admin hostnames + Host gating in the app + remove firewall Any/Any.

**Fallback:** Tunnel for patient/doctor only; staff/admin split-horizon to LAN IP with CIDR firewall; no public staff/admin DNS.

**Why not “VPN only” for staff without closing :3003?** Current Any/Any rule and all-interface listen mean VPN is not the actual boundary today.

### 3. Tunnel vs reverse proxy vs split-horizon vs Access?

**Recommended combination:** Tunnel + selective Access (+ optional later reverse proxy).

| Piece | Role |
| --- | --- |
| Tunnel | Eliminate inbound public NAT to 3003 |
| Access | Identity gate for staff/admin (MFA) without replacing app auth |
| Split-horizon | Fallback if Access/IdP not ready |
| Extra IIS/Caddy | Optional later for local TLS/path filtering; **not required** if Tunnel+loopback |

**Trade-off:** Access adds IdP dependency and possible double login; worth it for admin/staff PHI tools. Patients should **not** be forced through Cloudflare Access.

**Cost note (external research, verify at purchase):** Cloudflare Zero Trust Free for small teams (publicly advertised ≤50 users); paid Access commonly listed ~$7/user/month. Pricing can change — confirm in dashboard before relying on Free tier.

### 4. Tunnel connector on FILESERVER1 or separate host?

**Recommended initially:** FILESERVER1 (dedicated `cloudflared` service, least-privilege account).

**Evidence:** Single production app host; no second hardened connector host in current estate.

**Later:** Move connector to a separate internal host when HA/isolation budget exists.

**Downside:** App and tunnel share fate and compromise domain — accept for phase-1, monitor tunneling service separately.

### 5. Staff/Admin public DNS with Access vs internal-only DNS?

**Recommended:** Public DNS names **with Cloudflare Access** (primary).

**Reasoning:** Stable URLs for clinicians on approved devices; certificates automatic; avoids split-horizon failure modes; Access is the network authorization layer; app login remains.

**Internal-only DNS:** Valid fallback; risk of DNS leakage if someone later publishes a Tunnel hostname accidentally.

**Never:** Public DNS for admin with only “obscure hostname” and no Access/network restriction.

### 6. If Cloudflare, Tunnel, VPN, or IdP is unavailable?

| Outage | Effect | Mitigation |
| --- | --- | --- |
| Cloudflare/Tunnel | Public patient/doctor down | Status page; on-call; optional temporary LAN-only emergency procedure (documented, time-boxed) |
| Access/IdP | Staff/admin via CF blocked | Break-glass IdP accounts; LAN console access for admins on host; fallback split-horizon if pre-staged |
| VPN (fallback design) | Remote staff blocked | Same as today for remote; LAN may still work |
| FILESERVER1 | Total outage | Current SPOF — P1 HA discussion |

### 7. Minimum controls before exposing Patient or Doctor publicly

Must be **done and verified**:

1. Origin not publicly reachable (listen bind + firewall Any removed + external probe).  
2. ACL lockdown on `.env`, storage, logs, backups (+ secret rotation after exposure window).  
3. HTTPS via Cloudflare; Secure cookies validated in browser.  
4. CORS limited to HTTPS portal origins.  
5. **Host-based portal enforcement** in the application.  
6. WAF/rate limits on auth endpoints.  
7. Staff/admin not generally reachable (Access or non-routable).  
8. healthz + smoke login patient & doctor.  
9. Go/No-Go sign-off (Deliverable E).

SQL encrypt (`DB_ENCRYPT=true` with validation) is **strongly required before broad production acceptance**; if DBA cert work lags, document as **time-boxed exception** with compensating network trust — still prefer completing before public PHI.

Service account migration (off SYSTEM) is **P0 before public** preferred; if sequenced tightly, do not leave SYSTEM + world-readable `.env` together.

### 8. What should remain unchanged?

- H.5.4 server-side sessions / sessionStorage model (do not revert to legacy shared refresh).  
- LiveDB_ACE write prohibition and `DB_DATABASE` guard.  
- Result storage under `RESULT_STORAGE_ROOT` with authz on download routes.  
- Scheduled task + watchdog availability pattern (change identity, keep supervision).  
- OneClick backup-before-replace pattern (fix secret handling).  
- Existing RBAC / physician assignment / portal access-code **server** checks (harden, don’t bypass).

### 9. What is unnecessary / counterproductive now?

| Idea | Verdict |
| --- | --- |
| Four separate purchased domains | Unnecessary cost |
| Parent-domain cookies (`.acemccebu.results.com`) | **Counterproductive** — increases cross-portal cookie risk |
| Cloudflare Access for patients | Counterproductive UX; patients aren’t IdP users |
| Disabling `Secure` cookies to “make HTTP work” | Forbidden |
| Trusting `X-Forwarded-*` while :3003 remains world-reachable | Dangerous |
| Extra reverse proxy in front of Tunnel on day one | Extra failure mode without clear gain |
| Assuming subdomain = session isolation | False — requires Host gating |

### 10. Implement first, second, third?

1. **Origin containment + ACL + gitignore** (stop secret and port bleeding).  
2. **Tunnel + HTTPS + CORS/Host gating + firewall Any removal** (safe public path).  
3. **Access MFA for staff/admin + SQL TLS + service account** (privilege and crypto hardening).

### 11. Risks you may not have considered

- **Unified SPA bundle:** Admin UI JavaScript is likely downloadable from any hostname that serves `index.html`. Network blocks ≠ code confidentiality. Mitigate with Host-based SPA filtering or separate builds (P1).  
- **Access codes that do not expire** (source messaging in patients routes) — long-lived shared secrets; treat as P0/P1 product risk for public portal.  
- **CORS allows missing Origin** — non-browser clients bypass CORS (normal); do not confuse with authz.  
- **`trust proxy = 1`** while direct access exists enables header spoofing for IP-based limits.  
- **52 backup copies of `.env`** — rotation must include backup trees.  
- **C: volume ~4 GB free** (prior audit) — OS disk pressure can take down unrelated services during incidents.  
- **Local SQL Express listening on all interfaces** on FILESERVER1 — separate from portal DB host; still expands attack surface.  
- **Dirty git tree (515 paths)** — production builds may not be reproducible from commit alone.  
- **Cloudflare account takeover** — equivalent to edge MITM; require hardware MFA / break-glass.  
- **Double login (Access + app)** — plan UX communication for staff.  
- **WebSocket + Access** — needs explicit test; easy to break messaging.

### 12. Disagreements with the initial proposal

| Proposal element | Position |
| --- | --- |
| Four subdomains | Agree, with Host gating mandatory |
| Cloudflare for external access | Agree (Tunnel), not “DNS only to public IP” |
| Staff/Admin LAN+VPN only | Agree on **intent**; prefer Access on public hostnames **or** true non-routability — not hostname obscurity |
| Implied subdomain isolation | **Disagree** — insufficient alone |
| Implementing during planning | **Disagree** — correctly deferred; this doc stays planning-only |

## Rejected alternatives (summary)

1. **Port-forward 3003 to the internet with Cloudflare DNS-only** — rejects origin protection.  
2. **Cloudflare proxy to public WAN IP without Tunnel** — still requires inbound NAT and opens FW.  
3. **Single hostname with path-only separation** — worse UX and easier mistakes; still needs RBAC (paths alone fail).  
4. **Disable Secure cookies for compatibility** — rejects.
