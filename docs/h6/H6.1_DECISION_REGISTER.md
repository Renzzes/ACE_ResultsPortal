## 3. Identity provider — recommendation (OPEN)

**Status:** Pending evaluation. Owner selected “Other / evaluate.”

**Recommendation:** Prefer the **identity provider already managed by hospital IT**, if it satisfies:

| Requirement | Why |
| --- | --- |
| Staff/admin directory groups | Map to Cloudflare Access allow policies |
| MFA for admin (and preferably staff) | Admin Access MFA is required by architecture |
| User lifecycle (joiners/leavers) | Prevent orphaned Access grants |
| Break-glass / recovery | IdP or Access outage procedures |
| Access / sign-in logging | Incident response |
| Licensing compatible with Cloudflare Access | Seats and protocol (OIDC/SAML) |

**Evaluation order (suggested):**

1. Inventory what hospital IT already operates (commonly Microsoft Entra ID / Azure AD on Windows estates, or Google Workspace / other SAML/OIDC IdP).  
2. Confirm Cloudflare Access federation support for that IdP.  
3. Define `Results Staff` and `Results Admins` groups (names illustrative).  
4. Prove MFA for Admin Access policy.  
5. Document recovery accounts and offboarding SLA.

Do **not** invent a second IdP solely for ACE Results Portal if an existing hospital IdP meets the bar. Do **not** treat OTP-only Cloudflare one-time pins as the long-term staff directory unless IT accepts that operational model.

**Decision owner:** System owner / IT  
**Verification:** Written IdP selection, group names, MFA proof, and a denied-user Access test before Staff/Admin routes go live.

## 5. Staged implementation sequence (when later authorized)

Parallel preparation is allowed only where dependencies permit. Do not drop prerequisites to shorten the schedule.

1. Finalize architecture, domain, identity provider, network policy (LAN/VPN vs Access-remote), and DBA prerequisites.  
2. Review and approve the detailed P0 change plan / checklist.  
3. Harden secret-bearing file and storage ACLs using captured before-state evidence.  
4. Prepare least-privilege service identity and scheduled-task migration.  
5. Rotate exposed credentials after access controls are corrected (documented sequence + communications).  
6. Establish approved Tunnel and origin architecture; safely close direct-origin exposure.  
7. Implement and test Host gating, HTTPS-origin CORS, cookies, proxy trust, and portal routing.  
8. Validate SQL Server TLS with actual certificate verification.  
9. Implement and test access-code expiry/rotation **before** patient public launch.  
10. Validate Staff/Admin denial from unauthorized networks; confirm approved Access (and LAN/VPN if required) works.  
11. Complete external reachability and regression tests.  
12. Obtain a **separate documented Go/No-Go** before public DNS cutover or public patient/doctor exposure.
